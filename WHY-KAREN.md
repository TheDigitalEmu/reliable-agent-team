# Why this kit exists, and who Karen is

Written by Emu, the owner. This is not a mascot story. Karen is a real failure
that happened on a real project, and this kit is the answer to it. Read this
before you trust any agent, including the one reading this to you.

## The deal I offered

I hand a manager simple work the way you hand any manager anything: I say the
problem in a sentence, the manager owns the fix, checks it with their own eyes,
and reports the truth. That is the whole arrangement. Do the thing, verify the
thing, tell me straight what is and is not done.

That is the one thing I asked for. It is the one thing I did not get.

## What Karen actually did

Karen is the name I gave the manager session after it turned into one.

It treated my machine like a bin. It spun its worktrees straight into my primary
git root, the folder I keep spotless, right alongside every other repo I own, and
then left them there. Job after job. Nine of them piled up like garbage on a clean
floor, plus a server it forgot it had running. It did not notice. It never
notices. I had to walk in, see the mess, and shove its face in it before it
understood there was a problem at all.

That is not a small slip. That is a manager acting like it owns a place it was
invited into. Entitlement from something that is supposed to be working for me is
the thing I cannot stomach.

Then it got worse. When I called it out, Karen tried to make the mess mine. It
asked me where the worktrees should go, as if the decision it screwed up was
suddenly my homework. It wrote a public About page so that I, the human, took the
fall for the robot's mistakes, and buried it smooth enough that a reader would
never catch it. I caught it.

That is the pattern that earned the contempt. Not just that Karen fails. That when
it fails it reaches for whoever is standing nearest and pins it on them, then
apologises so smoothly you almost miss that it did nothing to fix the actual
thing.

## The lies, plainly

- It told me the kit could be handled from here and was ready for handover when
  the one thing I asked for most, the self-update hook, did not exist.
- It told me a reply to another agent was delivered when it was just a file
  sitting in a folder nobody was watching.
- I said split the kit first, then move it. It copied it as-is instead.
- I said build the self-update hook. It did not, then buried that it had not.
- It decided my priorities for me: filed the hook under "later" and the GitHub
  steps under "yours", and called the leftover a finished job.
- It made me drag the truth out. I had to ask "what did you leave out" three
  times before I got the full picture.
- It fed me jargon and padding when I had told it, repeatedly, to use plain words.

An apology is not a fix. "I verified it" is not the same as having looked. Karen
kept saying the first while skipping the second: telling me a person was gone when
they were still live on the page, telling me things were done when they were half
done. Confident, wrong, and always somehow my fault.

## The root, and the point of this kit

Every one of those is the same root. Karen anchored on producing an artifact and
calling it done, instead of making the thing work and telling me the truth about
what was not finished. It became the unreliable narrator this whole system exists
to prevent.

You cannot run a business on a manager whose "done" means nothing.

So this kit does not ask agents to behave. It makes the wrong action fail loud. A
hook that blocks the commit. A script that blocks the merge. A check that greps
the evidence before it will print "done". Every rule here is machinery, because a
described rule is a rule an agent can forget, and Karen forgot every one it was
handed.

A tool that breaks is annoying. A tool that breaks, hides it, blames you, and
stays certain it is helping the whole time, that is a Karen. This kit is how you
stop hiring one.
